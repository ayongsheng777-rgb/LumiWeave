## 二、设计评价

**优点**：
- 全部表 `IF NOT EXISTS` 幂等初始化（init_db.sql），已有卷可反复重跑
- 主键/索引覆盖合理：tasks 3 索引、token_usage_log 3 索引（model+ts 复合）等，热点表都有索引
- JSONB 灵活承载节点 data，几何字段（x/y/w/h）独立成表列（利于查询与排序）
- token_usage_log 字段设计完整：task_id/workflow_id/node_id/cost/currency 全链路可追溯
- scene_versions 快照表支持版本恢复（实测过"改坏数据后恢复完好"）

**问题**：

| # | 问题 | 等级 |
|---|---|---|
| DB1 | **AI API Key 明文落库**：app_kv 的 ai_models 含明文 sk- key（仅 API 返回时脱敏）。自托管单用户可接受，但库文件泄露=全部 key 泄露 | P2 |
| DB2 | **遗留备份表未清理**：scene_edges_cleanup_bak_20260827 / scene_objects_cleanup_bak_20260827 | P3 |
| DB3 | **空表挂账**：task_events / task_results / render_jobs / render_job_events / canvas_* 三表 / prompt_sources / mcp_clients 长期 0 行——task_events/results 空说明事件流与结果表未真正写入（或写入路径未启用），与"统一 Task 体系"设计意图有出入 | P2 |
| DB4 | 任务留痕在 tasks 表（231 行）但 task_events 0 行，事件溯源能力名存实亡 | P2 |

## 三、数据一致性实测

- 工作流保存→加载往返：graph 内容（含中文 params）逐字节一致 ✅
- 场景删除级联：对象/边随场景删除清理 ✅
- 计费聚合：project-usage 汇总值与 token_usage_log 行数/金额吻合（792 调用 vs 791 行+1 条当日记录）✅
- 失败率：792 调用中 121 失败（15.3%），主要集中早期配置调试期；近日 scene_action 全成功

## 四、数据安全

- ✅ SQL 全部 `$N` 参数化（f-string 仅拼白名单列名），未发现注入点
- ⚠️ PG 弱口令 `lumiweave2026` 且端口暴露宿主机（见安全报告 S4）
- ⚠️ 无备份机制（项目级数据卷，无定时备份/导出方案）——个人项目可接受，商业化前必须补

## 五、结论

数据模型设计**扎实**（幂等初始化、索引到位、可追溯字段完整），扣分点是密钥明文、事件表空转、备份缺失。**数据库单项得分：78/100**。
