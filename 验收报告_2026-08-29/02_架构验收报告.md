# 02 架构验收报告 — 绵绣 LumiWeave

> Phase 1：项目架构分析 ｜ 评分维度权重 20%

## 一、技术架构识别

**形态**：模块化单体（Modular Monolith）+ 前后端分离 + 独立 MCP 进程。

```
React 前端 (nginx:3010)
   │ /api 反代（强制 IPv4，已修 IPv6 坑）
FastAPI 后端 (uvicorn:8000←8900)
   ├── app/scene|workflow|canvas|director|film|renderers|providers|assets|...
   ├── app/services/      服务门面层（MCP 与 API v2 共用）
   └── app/mcp/           MCP Server（独立容器 :8901）
PostgreSQL 16 + Redis 7（Redis 为死依赖，见问题清单）
```

## 二、架构优点（真实落地，非文档空谈）

1. **统一 DAG 协议**：`schemas/workflow.py` 前后端唯一契约，`to_engine_graph()` 协议层/引擎层解耦
2. **服务门面层**：`app/services/` 供 MCP 工具与 REST API v2 复用，避免双份业务逻辑
3. **注册表驱动**：scene/registry.py 为唯一真源，加对象类型只改一处，前端自动出工具条与检查器
4. **统一 Task 体系**：tasks/task_events/task_results 三表贯穿，状态机完整，断线不判失败
5. **统一错误码**：AI 调用 7 类错误码（INVALID_API_KEY/TIMEOUT/...），实测超时返回结构化错误
6. **依赖全部精确锁版本**（requirements.txt 无 latest；mcp==2.1.0 经核实为真实版本）
7. **类型注解覆盖率 78.5%**，命名规范统一，无裸 `except:`

## 五、结论

架构设计水平**高于同类个人项目**：协议契约、门面层、注册表、统一 Task/错误码都是正确的大型系统做法。主要债务集中在：单文件巨型化（actions.py）、前端状态层重复、死代码/死依赖清理、测试体系形同虚设。**架构单项得分：82/100**。
